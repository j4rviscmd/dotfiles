# Forest Config スキル

## このスキルについて

プロジェクトを深く分析し、`.forest.toml` の最適な設定を提案・作成・更新する。
ルックアップテーブルではなく、プロジェクトの実際のファイル構造・中身を理解した上で
最適な `[start].commands`、`[start].share`、`[finish].commands` を推論する。

---

## ガードレール（絶対に守ること）

| ルール | 理由 |
| ------ | ---- |
| **CWDを分析対象とする** | 引数なしの場合は現在のディレクトリを分析 |
| **ユーザ承認後にのみファイルを更新** | 勝手に .forest.toml を書き換えない |
| **プロジェクトファイルを十分に読み込む** | 推測でなく実態に基づいて推論する |
| **既存の .forest.toml を尊重** | 既存設定がある場合は差分提案、上書きしない |

---

## 実行フロー

### Step 1: プロジェクトの徹底分析

CWD のプロジェクトを包括的に読み込む。テーブルのルックアップではなく、
実際のファイル構造と中身から自力で推論するための情報収集。

**必ず読み込むファイル**（存在する場合）:

- `.gitignore` — share推論の参考情報。「git管理外のファイル」の候補を把握する。ただし `.gitignore` にリストされている ≠ shareすべき（`.DS_Store` や `*.log` 等は不要）。LLMが**開発に必要なものだけ**を選別すること
- `package.json` — scripts, dependencies, workspaces の確認
- `Cargo.toml` — Rust の依存関係・ビルド設定
- `pyproject.toml` — Python の依存関係・ツール設定
- `requirements.txt` — pip の依存関係
- `go.mod` — Go のモジュール定義
- `Gemfile` — Ruby の依存関係
- `composer.json` — PHP の依存関係

**必ず探索するパターン**:

- `.env*` — 環境変数ファイル（開発に必要な資材の特定）
- `*lock*` / `*.lock` — ロックファイル（パッケージマネージャの特定）
- フレームワーク設定ファイル群（`next.config.*`, `nuxt.config.*`, `vite.config.*` 等）
- Docker関連（`docker-compose.*`, `Dockerfile*`）
- スキーマツール（`prisma/schema.prisma`, `drizzle.config.*`）

**必ず評価する「プロジェクト規模」**:

share判定に直結するため、以下を必ず調査する:

| 調査項目 | 確認方法 | 目的 |
| -------- | -------- | ---- |
| `node_modules/` 等のサイズ | `du -sh node_modules/` 等 | 再生成コストの評価 |
| `out/` / `dist/` / `build/` のサイズ | `du -sh out/` 等 | ビルド成果物のコピー vs 再ビルドの判断 |
| `.build/` やダウンロード済みバイナリの有無 | `ls -la .build/` 等 | Electron等の重いダウンロード資材の特定 |
| `npm ci` / `npm install` の所要時間（推定） | ロックファイルの行数や依存数から推定 | start.commands の `install` vs `ci` の選択 |

**プロジェクト規模の分類**:

| 規模 | 目安 | share方針 |
| ---- | ---- | --------- |
| 小規模 | `npm ci` が数秒〜1分、ビルドが数十秒 | 再生成推奨。share最小限 |
| 中規模 | `npm ci` が数分、ビルドが数分 | 環境変数のみshare |
| 大規模 | `npm ci` が10分以上、またはビルドが10分以上 | **重いディレクトリ（`node_modules`, `out`, `.build/` 等）もshare候補に含める** |

**アクション**:
1. `Glob` + `Read` を駆使してプロジェクト構造と中身を把握
2. プロジェクト規模を評価し、share方針を決定（上記テーブルに基づく）
3. `references.md` の原則を参照しつつ、プロジェクトの文脈に基づいて推論
4. 分析結果を変数として記憶

---

### Step 2: 推奨設定の推論

Step 1 で収集した情報に基づき、`references.md` の原則を適用して推論。

**推論すべき3つの設定**:

#### `[start].commands`

worktree作成直後に実行すべきコマンドを推論。
プロジェクトを理解した上で、開発を開始するために必要なセットアップを考える。

**推論の視点**:
- パッケージのインストール方法は？（ロックファイルから判断）
- インストール後に必要な生成ステップは？（Prisma generate 等）
- ビルドが必要か？（開発サーバー起動前にビルドが必要な場合）

#### `[start].share`

main から worktree にコピーすべき非git管理ファイルを推論。
`.gitignore` の内容を出発点とし、そのうち開発に必要なものをshare候補として選別する。

**推論の視点**:
- `.gitignore` に記載されているファイルのうち、worktree内で開発するために必要なものは何か？
- devサーバーを起動するためにどの環境変数ファイルが必要か？
- コピーすべきでない（コマンドで再生成すべき）ものは何か？
- **再生成に時間がかかる重いディレクトリはないか？**（大規模プロジェクトでは `node_modules/`, `out/`, `.build/` 等のshareが実務上必須）

**`.gitignore` 分析テーブルの作成**:

`.gitignore` が存在する場合、Step 4 の提案で以下のテーブルを **必ず** 表示する。
各行は `.gitignore` のパターンを分類し、shareに含めるか（○）除外するか（×）とその理由を示す。

```
## .gitignore 分析

| パターン | share | 理由 |
| --------- | :---: | ---- |
| `.env` | ○ | 開発用環境変数。devサーバー起動に必須 |
| `.env.local` | ○ | ローカル固有の環境変数オーバーライド |
| `.env.production` | × | 本番環境変数。worktreeでは不要 |
| `.env.test` | × | テスト用。worktreeで独立管理すべき |
| `node_modules/` | △ | 【規模依存】小規模なら再生成（×）、大規模ならshare（○） |
| `out/` | △ | 【規模依存】ビルド時間が長い大規模プロジェクトならshare（○） |
| `.build/` | △ | 【規模依存】Electron等の重いダウンロード資材ならshare（○） |
| `dist/` | × | ビルド成果物。コマンドで再生成可能 |
| `.DS_Store` | × | OS生成ファイル。開発に無関係 |
| `*.log` | × | ログファイル。開発に無関係 |
| ... | ... | ... |
```

**判定基準**:

| 判定 | 条件 | 例 |
| :--: | ---- | -- |
| ○ | 環境変数ファイルで開発に必要 | `.env`, `.env.local`, `.env.development` |
| ○ | 開発用の秘密鍵・サービスアカウント | `serviceAccountKey.json`, `gcloud-key.json` |
| ○ | コマンドでは再生成不可なローカル設定 | `firebase.json`（ローカルエミュレータ設定） |
| ○ | **再生成に10分以上かかる重いディレクトリ**（大規模プロジェクト） | `node_modules/`（数GB）, `out/`（数百MB）, `.build/electron/`（ダウンロード済みバイナリ） |
| × | 再生成が高速（1分未満）なパッケージ・依存関係ディレクトリ | `node_modules/`（小規模）, `vendor/`, `.venv/` |
| × | 再生成が高速なビルド成果物 | `dist/`, `.next/`, `target/` |
| × | OS・エディタ生成ファイル | `.DS_Store`, `.idea/`, `*.swp` |
| × | ログ・キャッシュ | `*.log`, `__pycache__/`, `.cache/` |
| × | 本番・テスト用環境変数 | `.env.production`, `.env.test` |
| × | コメント行・空行 | `# ...`, （空行） |

**重要**: 「再生成可能だから×」と機械的に判断しないこと。大規模プロジェクトでは、`node_modules/` の `npm ci` に15分以上、`out/` のフルビルドに20分以上かかることがある。この場合、数十秒のコピー vs 数十分の再生成 であり、shareが圧倒的に合理的。

**表示ルール**:
- コメント行と空行はテーブルから除外する
- パターンが類似している場合はまとめて表示してよい（例: `.env.test` / `.env.production` → 「テスト/本番用環境変数」）
- share に含まれないパターンが大半であることを前提とし、除外理由を明確に示すことでユーザーの信頼を得る

#### `[finish].commands`

worktree削除後にmainで実行すべきコマンドを推論。
主に「worktreeでの変更をmainに同期する」のが目的。

**推論の視点**:
- worktree内で依存関係が変わった可能性は？（package.json等の変更）
- main側で依存関係を再インストールすべきか？

---

### Step 3: 既存 `.forest.toml` との比較

1. CWD に `.forest.toml` が存在するか確認
2. 存在する場合は `Read` で内容を取得
3. Step 2 の推論結果と比較し、差分を分類:

| 分類 | 説明 |
| ---- | ---- |
| 追加 | 現在の設定にない項目 |
| 変更 | 現在の設定と異なる値 |
| 削除 | 不要と思われる項目 |
| 維持 | 現在の設定が適切 |

---

### Step 4: ユーザへの提案

**提案フォーマット**:

`.forest.toml` が **ない** 場合:

```
## プロジェクト分析結果

（プロジェクトタイプ、パッケージマネージャ、環境ファイル等の分析サマリ）

## .gitignore 分析

| パターン | share | 理由 |
| --------- | :---: | ---- |
| ... | ○/× | ... |

## 推奨設定（新規作成）

.forest.toml は見つかりませんでした。以下の設定で作成します：

[start]
commands = [...]
share = [...]

[finish]
commands = [...]

### 推論の根拠

- commands: （なぜこのコマンドが必要か）
- share: （.gitignore 分析テーブルの○項目から選定した理由）
```

`.forest.toml` が **ある** 場合:

```
## プロジェクト分析結果

（プロジェクトタイプ、パッケージマネージャ、環境ファイル等の分析サマリ）

## .gitignore 分析

| パターン | share | 理由 |
| --------- | :---: | ---- |
| ... | ○/× | ... |

## 現在の設定

（現在の .forest.toml の内容）

## 提案する変更

- [追加/変更/削除] （具体的な差分とその理由）

## 更新後の設定

（更新後の .forest.toml の内容）
```

**アクション**:
1. 提案内容をユーザに表示
2. `AskUserQuestion` で承認を確認

---

### Step 5: 承認後のファイル更新

1. ユーザが承認したら `Write` で `.forest.toml` を作成/更新
2. 更新内容を確認メッセージで表示

**更新時の注意**:
- 既存のコメントは可能な限り保持
- 新規作成時はフォーマット済みのTOMLを出力

---

## エラー発生時の処理

| ケース | 対応 |
| ------ | ---- |
| プロジェクトタイプを判定できない | ユーザに判定結果を報告し、手動設定を促す |
| 環境ファイルが1つも見つからない | share を空欄にして提案（警告なし） |
| ユーザが提案を拒否 | 変更せずに終了 |
